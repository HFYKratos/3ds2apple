# Launcher-first architecture (S2Arm-style) — corrected product plan

> The user's target: a **Windows launcher and a macOS launcher**. The user imports a 3DS ROM
> into the launcher; the launcher builds the native AOT files; it installs the base iPhone/iPad
> shell IPA through a **built-in Impactor/signing flow**; then it copies the imported game/ROM
> into the app's designated folder on the phone. One shell app holds the whole library.

This replaces the earlier dev-only model (a self-contained IPA with the ROM bundled; useful for
simulator proof, wrong for the product).

## S2Arm reference (studied from /mnt/f/project/S2Arm-study, Apache-2.0)

- `LAUNCHERS/macos` (SwiftUI) and `LAUNCHERS/windows` (C# launcher) drive import → build →
  sign/install → push game resources.
- **Windows signing/install**: the launcher bundles the **official Impactor v2.7.2 + `plumesign`
  CLI** unmodified (SHA-256 pinned; Impactor is MIT and embeds `apple-codesign` MPL-2.0).
  It opens Impactor for the user's Apple ID login and invokes `plumesign` to sign/install the IPA.
  S2Arm does not implement its own signing. macOS uses Xcode provisioning/signing +
  `xcrun devicectl`, with Impactor being the Windows path.
- **Pushing game files**: `PACK/devpush` (Rust, `idevice` crate) talks to usbmuxd, then uses
  `house_arrest` `VendContainer` + **AFC** to write into the installed app's container
  (Documents). It supports put/get/ls/put-tar, progress reporting, a 90s stall watchdog,
  device listing, IPA install/uninstall, and app-attribute queries.
- The base shell app is installed once; per-game packs/resources are pushed to the app
  container; the shell library scans them. No game data in the IPA.
- Windows bundles a Python/.NET/Git runtime for its build pipeline; Mac uses Xcode natively.

## Target for 3ds2apple

### User flow
1. Install the Windows or macOS launcher.
2. Import one or more decrypted `.3ds`/`.cci` files.
3. Launcher detects titleID/name and compiles the AOT GamePack + prepares game data.
4. Connect iPhone/iPad, open Impactor (Windows) or Xcode signing (macOS) once, sign in with
   the user's own Apple ID.
5. Launcher installs/updates the **base shell IPA** (unsigned app signed by Impactor/Xcode).
6. Launcher pushes the game package + ROM into the app's Documents folder via the device
   bridge (AFC/house_arrest), with progress and resume/stall handling.
7. Phone shell shows the whole library; no on-phone import.

> **Correction (2026-11-14): iOS will not dlopen an unsigned dylib copied into Documents.**
> Per-game AOT `GamePack.dylib` files must be inside the **signed IPA**. The launcher therefore
> builds a ROM-free IPA containing the base shell + `Frameworks/GamePack-<TITLEID>.dylib` + catalog,
> signs/installs it with Impactor/Xcode, and **only pushes ROM/game data + GameInfo.json** into
> Documents/Games. Adding/removing games rebuilds the IPA catalog/packs and reinstalls it;
> pushed ROM data is kept. The shell loads the pack from the app bundle and the ROM from Documents.

### On-device layout (proposal)

```text
Documents/
  Games/<TITLEID>/
    GameInfo.json        # titleID, displayName, hashes, sizes (pushed with the ROM)
    GameRom.cci          # user's decrypted game data (pushed; never in the public IPA)
# The AOT code is NOT here: GamePack-<TITLEID>.dylib lives in the signed IPA bundle
# (Frameworks/) plus the bundle GameCatalog; iOS rejects unsigned code in Documents.
  Library/state.json     # optional library cache/state written by shell or launcher
```

Base shell IPA carries a `GameCatalog.json` generated by the launcher (one entry per imported
AOT game, with `packFile` in `Frameworks/`). `Documents/Games/<TITLEID>/GameInfo.json` +
`GameRom.cci` provide the pushed game data. Launch resolves the pack in the app bundle and the
ROM in Documents; the library is catalog-driven, with Documents data availability shown per game.

### Components to build

| Component | Responsibility |
|---|---|
| `launcher/macos` | SwiftUI launcher: import ROM, build, install base shell via Xcode/devicectl, push files with devpush, progress/library/errors. |
| `launcher/windows` | Windows launcher (C#/WinUI/WPF or Tauri): same flow; bundles official Impactor + plumesign; uses devpush for container writes. |
| device bridge (`tools/devpush` or `builder/device`) | Rust `idevice`/AFC tool: devices, install/uninstall, app-attr, put/get/ls/put-tar, launch; progress + stall watchdog. |
| signing/install wrapper | Locate/invoke bundled Impactor + plumesign (Windows) or Xcode (`xcodebuild`/`devicectl`) on macOS; SHA-256 pinned, licenses preserved; no custom signing server. |
| shell Documents library | Scan Documents/Games, launch from there, no bundled ROM, file sharing enabled; optional fallback for simulator/dev. |
| build orchestration | Windows and macOS compile paths; Windows may use a bundled cross toolchain, a local macOS build agent, or prebuilt shell + pack compiler—research required. |

### Licensing / distribution

- S2Arm is Apache-2.0; Impactor is MIT and embeds apple-codesign MPL-2.0. If bundling official
  Impactor binaries, keep the original files unmodified, pin SHA-256, include licenses and
  source links in `THIRD_PARTY.md`/`NOTICE`; do not claim we wrote it.
- Never distribute ROMs or ROM-bundled IPAs; users import their own games.
- The base shell IPA is ROM-free and can be signed by the user's Apple ID.

### What exists already and is reused

- AOT-only shell + GamePack ABI/dynamic loading (works in simulator).
- `builder/pack` CLI: ROM header detection, queue, package/catalog generation, `--include-rom`.
- `build-game-pack.sh` / `build-multi-game-ipa.sh` and x86 simulator runtime.

### Known hard part

Windows launcher must compile game packs. S2Arm ships a bundled Windows build runtime; for our
C/clang-based AOT pipeline we need to verify whether we can bundle a legal cross toolchain or
must drive a macOS build agent. This is investigated separately; the launcher UI and device
bridge do not depend on that decision.

## Device bridge and install/push contract (2026-11-14, task-16)

- Implemented: **tools/devpush** (Rust: devices, install/uninstall, app-attr,
  put/get/ls/stat/put-tar/mkdir/rm/free, usbmuxd USB/Wi-Fi, house_arrest
  VendContainer/VendDocuments + AFC, progress events, 90 s stall watchdog,
  filesystem mock backend, tests), **builder/device** (Python wrapper:
  readiness, official-Impactor plumesign signing/install, game push/verify,
  NDJSON for launchers), **scripts/impactor** (official Impactor v2.7.2 +
  plumesign fetch/verify, SHA-256 pinned, MIT/MPL-2.0 licenses + source links).
- Authoritative contract: **docs/device-bridge.md** (devpush/1 for the bridge,
  device-install/1 for the wrapper). Launchers: call
  builder/device/device_cli.py status -> sign-install -> push-game/verify-game,
  or call devpush directly for raw container operations with the same JSON and
  exit-code contract.
- No Apple ID implementation: login stays in Impactor/Xcode; bundled official
  binaries are unmodified and hash-verified. Xcode/devicectl is the macOS
  fallback for already-signed IPAs.
- Data layout (Lead correction 2026-11-14): executable code stays in the signed
  IPA - per-game GamePack.dylib + GameCatalog are embedded by the launcher/build
  step and IPA signing covers nested dylibs. Documents/Games/<TITLEID>/ holds
  only GameRom.cci + GameInfo.json; push-game pushes ROM then GameInfo.json last,
  never executable code, then verifies size/sha256. Pushed ROM data persists
  across shell reinstall/update.
- Real device unavailable to agents: host-side compile/tests + documented manual
  device test (docs/device-bridge.md sections 7 and 11).
