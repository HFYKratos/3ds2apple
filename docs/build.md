# Build guide

This guide builds the app on macOS with Xcode and packages an unsigned IPA.
It does not include or require any game data in the repository; you need your
own legally obtained, decrypted `.3ds` / `.cci` for the game build step.

The **AOT-first desktop flow** (import several ROMs on a computer, build one
package per game, then package one shell IPA carrying all of them) is a preview
documented in [desktop-aot.md](desktop-aot.md). It is driven by the Rust CLI in
[../builder/pack](../builder/pack) and the new scripts
`build-game-pack.sh` / `build-multi-game-ipa.sh`; on Linux/Windows it can run a
complete fake/dry-run pipeline (labelled placeholder packs) without Xcode.

## Requirements

- **Build machine: macOS Tahoe 26.2–26.x + Xcode 26.6 with the iOS 26.5
  SDK** (tested; Intel and Apple Silicon). This is a build-tool requirement
  only.
  - **The app's minimum runtime stays iOS 16.** Xcode 26.6 supports
    deployment targets iOS 15–26.5, so the project's `iOS 16.0` target builds
    unchanged; do not raise the user-facing iOS minimum just because the
    build Xcode changed.
  - Xcode 27 requires an Apple Silicon Mac and macOS Tahoe 26.6+; it is an
    optional future toolchain, not the minimum here. Xcode 26.6 remains the
    pinned, tested baseline for reproducible release builds.
  - Xcode 26 simulator runtimes no longer include Intel support by default;
    this build VM still runs the installed iOS 26.5 x86_64 simulator, but a
    future move to Apple Silicon is recommended for simulator testing.
- Rust stable with the `aarch64-apple-ios` target. For the iOS Simulator
  runtime, also add `x86_64-apple-ios` (Intel build host) or
  `aarch64-apple-ios-sim` (Apple Silicon host).
- `xcodegen` (for the SwiftUI project).
- Python 3.
- For a game build: a local checkout/toolchain of
  [3dsrecomp](https://github.com/fearkov/3dsrecomp) and
  [Zakuro](https://github.com/fearkov/zakuro), or the scripts in this
  repository (they clone/pin them).

```bash
rustup target add aarch64-apple-ios
xcode-select -s /Applications/Xcode.app
```

## 1. Build the runtime static library

```bash
scripts/build-zakuro-ios.sh
```

The script clones/pins Zakuro into `third_party/`, applies the local patches
from `ios/zakuro-ios/patches/` (idempotently; an already-patched checkout is
left alone), adds the `ios/zakuro-ios` crate, disables the shader JIT, builds
for `aarch64-apple-ios` and places `build/ios/libzakuro_ios.a`. The patches are
the iOS MoltenVK lookup and the 5 s pipeline-cache save interval; a per-game
rebuild with `build-linked-ios-lib.sh` applies any missing patch again.

For a per-game AOT build, the linked variant is built with:

```bash
ZAKURO_LINKED_PROGRAM_ID=<16-hex-title-id> \
  cargo build -p zakuro-ios --release --features linked \
  --target aarch64-apple-ios
```

## 2. Build the shell app (no game)

```bash
scripts/build-ios-app.sh
```

This runs `xcodegen`, `xcodebuild` for `iphoneos` with code signing disabled,
and prints the `.app` path. It links the interpreter-only static library.

The shell build writes an **empty** `GameCatalog.json` (no AOT games) into
`ios/app/Resources/` for the duration of the build, then removes it (or restores
a file that existed before), so `git status` stays clean. To bundle a
pre-generated catalog instead (advanced, e.g. several AOT games in one app):

```bash
scripts/build-ios-app.sh --game-catalog build/catalog/pokemon-y.json
```

## 3. Two IPA tracks: shell IPA vs game IPA

The repository follows the S2ARM split: **the macOS build machine compiles
everything; the iPhone only selects and launches**. AOT code is linked into the
app at build time - the device never recompiles a ROM, and no ROM or generated C
is ever committed.

| Track | Build command | App contents | IPA name |
|---|---|---|---|
| Shell IPA | `build-ios-app.sh` then `package-ipa.sh` | interpreter runtime only; empty catalog | `3ds2apple-shell-<version>.ipa` |
| Game IPA | `build-recomp-ios.sh` -> `build-linked-ios-lib.sh` -> `build-game-ipa.sh` | linked runtime + `libgame.a` for one title + one-game catalog | `3ds2apple-<game>-<version>.ipa` |
| Multi-game shell IPA (AOT-first preview) | per game: `build-recomp-ios.sh` -> `build-linked-ios-lib.sh` -> `build-game-pack.sh`; then `build-multi-game-ipa.sh --base-app ...` | linked packs (`GamePack-<TITLE>.dylib`) for several titles + schema-v2 catalog | `3ds2apple-multi-game-<version>.ipa` |

On a game IPA the selected ROM runs the linked AOT code; on a shell IPA (or for a
ROM that is not in the catalog) the runtime uses the interpreter fallback.

### GameCatalog.json

`GameCatalog.json` is generated by the build, never committed (it is
gitignored), and copied into the root of the `.app` bundle.
`ios/app/Sources/GameCatalog.swift` reads it to know which title IDs have AOT
code linked in:

```json
{"schemaVersion":1,"games":[{"titleID":"0004000000055E00","displayName":"Pokémon Y","productCode":"CTR-P-EKJA","aot":true,"aotVersion":1,"notes":""}]}
```

- `build-ios-app.sh` without `--game-catalog` writes
  `{"schemaVersion":1,"games":[]}` (interpreter-only shell);
- `build-game-ipa.sh` writes exactly one entry, filled from the linked title ID,
  `--display-name`, `--product-code` and `--aot-version`;
- `package-ipa.sh` validates the catalog inside the `.app` and prints
  `CATALOG: games=N; AOT: <title> (<titleID>)` before packaging.

## 4. Build a per-game AOT IPA

The scripts implement the split pipeline: 3dsrecomp can run on Linux or macOS;
the generated C is compiled for iOS on macOS; the app links `libzakuro_ios.a`
and `libgame.a`.

```bash
# 3dsrecomp -> build/game/<name>/  (C + static archive)
scripts/build-recomp-ios.sh "ROM/pokemon-y.cci" pokemon-y --auto-serial

# linked runtime + game archive -> build/ios/<name>/
scripts/build-linked-ios-lib.sh pokemon-y

# Xcode app + one-game catalog + IPA -> IPA/3ds2apple-pokemon-y-0.1.2.ipa
scripts/build-game-ipa.sh pokemon-y \
  --title-id 0004000000055E00 \
  --display-name "Pokémon Y" \
  --product-code CTR-P-EKJA
```

`--title-id` is normally inferred from
`build/ios/<name>/build-info.txt`, so it can be omitted;
`--display-name`/`--product-code` are catalog metadata and
`--aot-version` defaults to `1`. The IPA version is the app's
`CFBundleShortVersionString` (`project.yml` `MARKETING_VERSION`), so the
file is `3ds2apple-<game>-<version>.ipa`; override it with
`--ipa-version` or set the name explicitly with `--ipa-name`.

See [scripts/README.md](../scripts/README.md) and
[scripts/AOT_BUILD.md](../scripts/AOT_BUILD.md) for options, incremental
builds, serial-compile fallbacks and failure diagnostics.

### Verification

For a game build, the runtime logs whether the linked code was accepted. On
device, the app's status area shows `AOT: linked, active` when the generated
code is executing, or `linked, interpreting` when the title/ABI did not match
and the interpreter is used. The build also proves that the catalog ships inside
the app:

```bash
unzip -p IPA/3ds2apple-pokemon-y-0.1.2.ipa Payload/3ds2apple.app/GameCatalog.json
grep -E '^(title_id|game_catalog_title_id|ipa_sha256)=' build/ios/pokemon-y/manifest.txt
```

## 5. Package and install

Shell IPA:

```bash
scripts/package-ipa.sh ios/app/build/Release-iphoneos/3ds2apple.app 3ds2apple-shell-0.1.2
```

`package-ipa.sh` validates the bundle's `GameCatalog.json` when present and
prints the game count and AOT title(s), e.g.
`CATALOG: games=1; AOT: Pokémon Y (0004000000055E00)`. A shell app reports
`CATALOG: games=0; interpreter shell (no AOT games)`. (Game IPAs are packaged
by `build-game-ipa.sh` itself with the same script.)

The IPA is unsigned. Sign and install it with Sideloadly or AltStore using your
own Apple ID. The app is not intended for App Store distribution.

## 6. AOT-first desktop flow (multi-game shell IPA, preview)

The AOT-first model builds **one package per game** on the computer and one
**shell IPA** that carries several packages; the phone then only lists them from
`GameCatalog.json` and launches an already compiled pack. This is the preview
implemented in this tree; the full contract is in
[desktop-aot.md](desktop-aot.md).

```bash
# Desktop side (Linux/Windows/macOS; no Xcode needed for this part)
cd builder && cargo build -p builder-pack --release
CLI=target/release/3ds2apple-pack

# 1. import the user's own decrypted ROMs (headers only; nothing copied/hashed)
"$CLI" packages add --roms "ROM/Pokémon Y.cci" "ROM/Pokémon Alpha Sapphire.cci"
"$CLI" packages list
"$CLI" build --queued            # print the exact macOS build plan
"$CLI" build --queued --fake     # OR: preview packs locally (not installable)

# 2. macOS: real AOT packs through the existing scripts
scripts/build-game-pack.sh pokemon-y-00055e00 --title-id 0004000000055E00 \
  --display-name "Pokémon Y" --product-code CTR-P-EK2A --out out \
  --dylib <runtime-provided GamePack.dylib>

# 3. one shell IPA with the selected games (unsigned)
"$CLI" pack --all --execute --base-app ios/app/build/Release-iphoneos/3ds2apple.app

# Linux/Windows layout preview (fake shell app, placeholder packs; NOT installable)
scripts/build-multi-game-ipa.sh --packages-dir out/packages --all \
  --allow-placeholder-dylibs --fake-shell
```

Outputs: `out/packages/<TITLE_ID>/{GameInfo.json,GamePack.dylib}`,
`out/packages/GameCatalog.json`, `IPA/3ds2apple-multi-game-<version>.ipa` and
`IPA/<name>.pack-manifest.txt` (all gitignored). The catalogue is schema version
2 (`packFile`, `packABIVersion`, optional `registrationSymbol`/`coverFile`);
legacy version 1 catalogs are still accepted by the shell and by
`scripts/lib/game-catalog.sh`.

Behaviour notes: `build --roms ...` exits 1 if any requested ROM could not be
imported (accepted ROMs are still built/planned); `--fake` cannot be combined
with `--execute`; `build --queued --force` rebuilds packages that already have a
pack. The desktop CLI and the new scripts are documented in
[desktop-aot.md](desktop-aot.md).

Not done yet in this preview: the runtime hand-off that starts a game from a
`GamePack.dylib` (runtime-ffi task), the real `--from-libs` dylib link (unverified
on macOS), nested-dylib re-signing on device, a generate-only 3dsrecomp mode for
a fully Linux-native recomp step, and the Windows/macOS GUI launchers. See
[desktop-aot.md §10](desktop-aot.md).

Proof without Xcode: `cargo test -p builder-pack` and
`bash scripts/tests/desktop-aot-selfcheck.sh`.

## Troubleshooting

- **Undefined `_recomp_*` symbols**: `-lzakuro_ios` must come before
  `-lgame`; the game archive resolves the generated tables.
- **`AOT: linked, interpreting`**: the linked code's title ID or ABI does not
  match the ROM/runtime. Rebuild with the matching title and the same pinned
  revisions.
- **`Found no destinations`**: use `-target`/`-sdk iphoneos` rather than a
  simulator scheme if the iOS simulator runtime is not installed.
- **`PRODUCT_NAME` empty / `.app` with no name**: keep `PRODUCT_NAME` and
  `EXECUTABLE_NAME` explicit in `ios/app/project.yml`.
- **No game data**: this repository never contains ROMs. The app asks for a
  ROM at runtime; the game build needs a local copy on the build machine.
- **A local patch does not apply**: upstream `main` has moved on. Pin the
  tested revision (see [METAL.md](../ios/zakuro-ios/METAL.md) §8.2), re-apply
  the patches by hand, or update the patch file; the build continues without a
  failed patch (set `ZAKURO_STRICT_PATCHES=1` to make it fatal).
- **First load shows "Preparing graphics…" for a while**: this only happens
  when the optional graphics warm-up is enabled in Settings (off by default).
  It is bounded at 5 s and has a Skip button; a second load with the pipeline
  cache on disk is quicker. A build that fell back to the software renderer
  has no pipelines to warm and is revealed immediately; see
  [METAL.md](../ios/zakuro-ios/METAL.md) §10 for the log lines and diagnostics
  fields that verify this on device.
- **`the built app contains no GameCatalog.json`**: XcodeGen did not copy
  `ios/app/Resources/GameCatalog.json`. Re-run the build (the scripts run
  `xcodegen generate` themselves), check that `ios/app/project.yml` still
  bundles `Resources/`, and do not commit or hand-edit the generated catalog.
- **`invalid GameCatalog.json`**: the catalog is generated from the linked
  build, so re-run `scripts/build-game-ipa.sh <name>` instead of editing it.
  With `--game-catalog`, validate the file with
  `python3 -m json.tool <GameCatalog.json>`; title IDs are 16 upper-case hex
  digits and `aot: true` requires `aotVersion >= 1`.
